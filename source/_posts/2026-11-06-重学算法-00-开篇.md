# 为什么是「重学」

先交代动机，因为动机决定路线。

我见过太多人（包括我自己）掉进同一个坑：**把「认得」当成「会了」**。

看到「二分查找」点头，看到「红黑树」点头，看到「动态规划」也点头。真到要写，二分查找的边界能错三个地方；红黑树只记得「它是平衡的」；动态规划永远想不出状态怎么定义。

问题出在：**第一次学的时候，是在「知道有这个东西」的层面过的关，而不是在「能用它解决问题」的层面。**

所以这次重学，我给自己立了三条规矩，也当作这个系列的写作原则：

1. **每个结构都自己实现一遍**，不用现成库。不自己写一次，你永远不知道它的代价在哪。
2. **每个结论都要有可运行的证据**。这一系列的代码都在仓库的 `ds-course/` 目录下，`npx tsx` 就能跑。我说「O(n²) 翻倍会慢 4 倍」，就得有实测数字摆在那。
3. **分清「观察到的」「推断的」「不知道的」**。静态分析没看到执行，就不能说它运行时会怎样。这一条是我做逆向分析的老本行，放在学算法上一样成立——大部分「我以为我懂了」，都是把推断当成了事实。

# 为什么用 TypeScript

不是因为它最适合讲算法——那个位置属于 C。选 TypeScript 有三个很实际的理由：

- **泛型是真的泛型**。写一个 `Stack<T>`，类型系统会帮你把「这个栈里放的是什么」钉死，不用像 C 那样每换一个类型重写一遍，也不用像 Python 那样全靠自觉。
- **严格模式能当静态检查用**。开了 `strict` 和 `noUncheckedIndexedAccess`，`arr[i]` 的类型是 `T | undefined` 而不是 `T`——这一个设置就能拦掉一大堆「我以为不会越界」的 bug。
- **它离工程近**。学的目的是用。在 TypeScript 里踩到的坑（类型收窄、联合类型、结构兼容），和工作里写代码踩的是同一批。

代价也说清楚：TypeScript/JavaScript 的数组是动态的，`number` 是双精度浮点。讲到位运算、讲整数溢出时，我会明确标出这些和 C/Java 的差异，不含糊过去。

# 路线图

按「先有衡量标准，再谈结构」的顺序走。顺序不是随便排的——没有复杂度分析当尺子，学结构就变成背性质。

| 阶段 | 内容 | 核心问题 |
| --- | --- | --- |
| 0 | 复杂度分析 | 怎么衡量一个做法的好坏？ |
| 1 | 数组、动态数组、链表 | 连续内存和离散节点，各自付出了什么代价？ |
| 2 | 栈与队列 | 两种最受限的线性结构，限才对 |
| 3 | 哈希表 | 怎么用 O(1) 换一份不确定性？ |
| 4 | 树与二叉树 | 怎么把 O(n) 的查找砍成 O(log n)？ |
| 5 | 二叉搜索树与平衡树 | 树退化成链表怎么办？ |
| 6 | 堆与优先队列 | 怎么只取最值，而不付全排序的代价？ |
| 7 | 并查集与字典树 | 两个「为一类问题而生」的结构 |
| 8 | 图 | 关系型数据的通用表示 |
| 9 | 排序 | 从 O(n²) 到 O(n log n) 再到 O(n) |
| 10 | 算法范式 | 分治、贪心、动态规划、回溯 |

每一篇的固定结构：**动机 → 自己实现 → 复杂度分析（带实测）→ 易错点 → 练习**。

练习我不给标准答案，给「怎么验证自己对了」的方法。这个比答案重要。

# 怎么学才不白学

三条，都是踩过坑换来的：

**一，先自己写一遍，再看答案。** 顺序反了，你会产生「我看懂了」的错觉。看懂和能写出来之间隔着一次真实的思考过程。

**二，复杂度要能口算。** 不是背表，是看到一段代码能数出来。这个技能比记住任何单个结构都值钱，因为它能让你在写代码的时候就避开 O(n²)。

**三，接受「暂时不懂」。** 动态规划、平衡树这些，第一次学不懂是正常的。我的做法是标记下来，继续往前走，很多时候后面的内容会把前面的照亮。卡死在一处不动，是最低效的路径。
