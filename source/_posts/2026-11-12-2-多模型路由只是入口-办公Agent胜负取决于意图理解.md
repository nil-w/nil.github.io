## 路由只是入口，办公 Agent 的胜负落在意图理解

多模型接入能解决“用哪个模型”，解决不了“用户到底想做什么”。豆包工作加入第三方模型后，办公 Agent 的竞争才真正进入下一层：谁能把一句自然语言，稳定地落到正确的任务、上下文和权限上。

我最初把办公 Agent 的竞争理解成模型能力叠加。模型越多，用户选择越多，产品看起来也更强。后来做 Hermes Agent 的记忆改造，我才发现入口层很容易被复制。模型可以接入，Auto 路由可以配置，用户也能手动切换。但系统能不能听懂任务，取决于记忆、权限和执行链能否协同。

这次豆包工作的更新，正好把这条链路摆到了台前。它在自研的豆包2.1 Lite和Pro之外，接入Kimi K3.1 Pro、GLM 5.3、DeepSeek V4.1 Flash等第三方模型，并标出额度消耗倍率。用户可以按任务复杂程度、响应速度和使用成本选择模型。

> 模型数量决定可用范围，意图落点决定任务结果。

易观分析发布的2026年三季度办公智能体市场报告显示，今年9月，WorkBuddy的月访问量达到8534万次，豆包工作则为3039万次，前者约为后者的2.8倍。

这组数字改变了我原先的判断。多模型不是完整答案，入口规模才是当前可量化的差距。WorkBuddy已经接入混元、GLM、MiniMax、Kimi、DeepSeek等多家模型，并提供Auto模式。豆包工作随后跟进，说明多模型正在变成基础配置。

但访问量只能说明入口有多大。它无法解释用户进入以后，任务完成率如何，误操作多少次，也无法说明一次任务到底调用了几个模型。我到现在也没搞明白，办公 Agent 的真正壁垒会落在模型效果、记忆召回，还是权限治理。

## 路由解决选择问题，意图理解决定执行问题

用户说“把上周会议纪要整理成待办”，路由层最容易判断任务类型。写总结、列待办、提取负责人，模型可以按长度、速度和成本分配。难处出现在“上周”“会议纪要”“待办”分别指向什么。

这些词不能只靠一次 Prompt 解决。系统要知道上周指哪一段时间，哪场会议属于目标范围，待办应该写进哪里，谁有权修改。它们分别依赖时间语义、上下文召回和业务权限。

我在《AI 原生数据库的关键不是快而是理解意图》（2026-11-11）里写过，上下文决定意图能不能落地。做 Hermes Agent 记忆系统时，我也遇到过类似问题：系统记住了内容，用户换了表达，记忆就断了。《从零构建 Hermes Agent 记忆系统——memory-filtration-layer 迭代手记》（2026-05-22）记录的根因很直接，旧设计把记忆当成“对话录像机”，大量内容被写入，却无法稳定召回。

<span class="hl">记忆的任务不是保存更多内容，而是把当前意图连接到正确上下文。</span>

办公 Agent 也一样。路由负责把请求交给某个模型，记忆负责补齐任务对象，权限负责限定动作范围。三个环节缺一不可。模型再强，找错会议就可能整理错纪要。记忆命中了，也不能越过用户授权。路由选得便宜，更不能成为漏掉关键上下文的理由。

这也是多模型策略容易制造的错觉。把模型菜单做得丰富，用户得到的是选择权。办公 Agent 需要的却是更高的完成率。用户通常不想研究额度倍率，也不想判断哪款模型更适合某类任务。他们只关心事情有没有做完，以及做错时谁来负责。

> 多模型路由解决“由谁执行”，意图理解决定“执行什么”。

豆包工作此次调整价格，并下调豆包2.1 Lite和DeepSeek V4.1 Flash的额度消耗倍率，给新用户提供30天免费订阅权益。这些措施能降低试用门槛，也能扩大入口。可入口越宽，错误意图进入执行链的概率也越高。

## 权限必须和记忆一起设计

我过去做权限管理、流程引擎和低代码平台时，有一个很直接的感受：业务规则不是挂到模型前面的检查项。权限必须参与意图落地，因为同一个动作换个人、换一批数据，结果就可能完全不同。

Agent 记忆也存在同样问题。《改造 Hermes Agent 记忆系统：基于 MemPalace 的实践》（2026-05-01）提到旧记忆系统依赖固定 key。用户说“截图工具”，改成“微信截图”，系统就找不到。办公场景里的表达变化更复杂。“那份报表”“昨天发我的文件”“老板要看的版本”，每一句都需要关联具体对象。

如果记忆层只按关键词保存与召回，权限层再单独校验，最终得到的经常是两个彼此割裂的判断。系统找到了内容，却不知道当前用户能否引用；或者用户有权限，却因表达差异找不到内容。路由选中的模型再强，也只是在执行一个错误或残缺的任务。

<span class="hl">办公 Agent 的执行链应当是“识别意图、召回上下文、检查权限、选择模型”。</span>

这也解释了Auto模式的价值。自动路由减少界面操作，但它不能替代意图理解。路由策略如果只比较任务长度、模型速度或价格，得到的可能只是最低成本答案。真正可靠的Auto模式，需要先判断任务是否涉及敏感数据、跨系统写入和长期上下文，再决定模型与工具。

当前我仍有两个问题没有答案。第一，WorkBuddy的8534万次月访问量里，有多少来自真实任务完成，而非频繁试用？第二，豆包工作的3039万次里，第三方模型带来的新增使用能否转化为稳定留存？这些数据决定多模型窗口究竟是一次产品调整，还是长期入口策略。

未来的办公 Agent 可能不会向用户展示模型选择。用户只会提出目标，系统负责补齐上下文、申请权限并完成任务。到那时，多模型路由仍然重要，但它只占入口的一小部分。真正决定胜负的，是系统能否在正确权限内理解用户真正想完成的事情。
