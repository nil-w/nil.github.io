# 为什么先学复杂度，而不是先学结构

大部分人学数据结构的顺序是错的——先冲进链表、树、图，把「有哪些结构」背下来，很久以后才补复杂度。结果是：**手里有一堆工具，却没有判断该用哪一把的尺子。**

复杂度分析就是那把尺子。它的作用不是给你打分，是让你在写代码之前就能判断：这个做法在数据量放大 100 倍时，是会变慢 100 倍，还是 10000 倍，还是根本没感觉。

没有这把尺子，「优化」就只是手感；有了它，优化是可推理的。

# 大 O 到底是什么

先说清楚它**不是**什么。它不是运行时间的精确预测，跟机器快慢无关，也不告诉你一个程序要跑几毫秒。

大 O 描述的是一件事：**当输入规模 n 增长时，工作量增长的趋势。**

形式化一点：如果存在常数 c 和 n₀，使得对所有 n ≥ n₀ 都有 f(n) ≤ c·g(n)，就说 f(n) = O(g(n))。翻译成人话：

> n 足够大以后，f 的增长速度不会超过 g 的一个常数倍。

注意「足够大」这三个字。它意味着大 O **主动放弃了小规模时的表现**——这是它的力量所在，也是它的局限所在。后面讲误区时会回到这一点。

# 复杂度阶梯

从好到差排一遍，顺便给出「什么量级开始有感觉」的直觉：

| 复杂度 | 名字 | n=10 | n=1000 | n=100万 | 什么感觉 |
| --- | --- | --- | --- | --- | --- |
| O(1) | 常数 | 1 | 1 | 1 | 完美，随便涨 |
| O(log n) | 对数 | 3 | 10 | 20 | 极好，n 涨 1000 倍它才涨几倍 |
| O(n) | 线性 | 10 | 1,000 | 100万 | 良好，至少是线性的 |
| O(n log n) | 线性对数 | 33 | 10,000 | 2000万 | 很好，比较排序的下限 |
| O(n²) | 平方 | 100 | 100万 | 10¹² | 危险，n 过万就开始疼 |
| O(2ⁿ) | 指数 | 1,024 | 10³⁰¹ | — | 不可用，n=40 就爆炸 |
| O(n!) | 阶乘 | 362万 | — | — | 只能穷举，n>12 没戏 |

这张表值得背下来。不是为了考试，是为了建立量级感：**看到 n 的范围，你立刻知道能承受什么复杂度。**

- n ≤ 10：O(n!) 都行
- n ≤ 20：O(2ⁿ) 可以想想
- n ≤ 500：O(n³) 勉强
- n ≤ 5000：O(n²) 可以
- n ≤ 10⁶：O(n log n) 或 O(n)
- n ≤ 10⁸：只能 O(n) 或 O(log n)

# 怎么数：三条规则

数复杂度不是背结论，是看代码。三条规则够用了：

**规则一：顺序执行的代码，复杂度相加。**

```ts
function f(n: number): void {
  for (let i = 0; i < n; i++) doA();   // O(n)
  for (let i = 0; i < n; i++) {        // O(n)
    for (let j = 0; j < n; j++) doB(); // O(n)
  }
}
```

总的是 O(n) + O(n²) = **O(n²)**。加法规则下取增长最快的那项，慢的被吞掉。

**规则二：嵌套代码，复杂度相乘。**

上面第二段就是典型：外层 n 次，内层每次 n 次，合计 n × n = **O(n²)**。

嵌套深度是复杂度的指数级放大器。三层全嵌套就是 O(n³)。**看到嵌套循环，先数层数。**

**规则三：多项式取最高次项，常数系数扔掉。**

O(3n² + 100n + 1000) = O(n²)。为什么能扔？因为大 O 关心的只是「n 变大以后谁主导」。n=1000 时，3n² = 300万，100n = 10万，1000 忽略不计。

但要注意：**「能扔」不等于「不重要」。** 下一节就会看到，常数系数在真实世界里完全能决定胜负。

# 一个反直觉的例子：常数系数能压过阶数

规则三说常数系数可以扔，那是 n 足够大时的事。n 不够大时，阶数低的那个完全可能更慢。

```ts
// 算法 A：O(n)，但每次要做 1000 次操作
function a(n: number): number {
  let total = 0;
  for (let i = 0; i < n; i++) {
    for (let k = 0; k < 1000; k++) total += k; // 固定 1000 次，与 n 无关
  }
  return total;
}

// 算法 B：O(n²)，但每次只做 1 次操作
function b(n: number): number {
  let total = 0;
  for (let i = 0; i < n; i++) {
    for (let j = 0; j < n; j++) total += 1;
  }
  return total;
}
```

n = 10：A 做 1 万次，B 做 100 次。**B 快 100 倍。**
n = 10000：A 做 1000 万次，B 做 1 亿次。**A 快 10 倍。**

所以「O(n) 一定比 O(n²) 快」是错的。正确的说法是：**n 足够大时，O(n) 一定赢。** 而「足够大」是哪个点，取决于那两个被你扔掉的常数。

这就是为什么面试和实战里，算完大 O 还要再问一句：常数是多少？数据规模实际多大？

# 空间复杂度：同一把尺子，量的是内存

空间复杂度和时间复杂度是同构的，只是量的是「额外申请的内存量」而不是「操作次数」。

```ts
// O(1) 空间：只用了几个变量，与 n 无关
function sumLoop(arr: number[]): number {
  let total = 0;
  for (const x of arr) total += x;
  return total;
}

// O(n) 空间：新建了一个和输入等长的数组
function doubleAll(arr: number[]): number[] {
  return arr.map((x) => x * 2);
}

// O(n) 空间：递归深度为 n，每一层栈帧都要存
function factorial(n: number): number {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}
```

两个容易忽略的点：

**一，递归也算空间。** 上面那个 `factorial`，时间复杂度是 O(n)，空间复杂度也是 O(n)——不是 O(1)。每一层调用都要在调用栈上存一份局部变量和返回地址。递归写得太深会爆栈（Stack Overflow），那既是稳定性问题，也是空间复杂度问题。

**二，输入本身通常不算。** 惯例是只算「额外」申请的空间。`doubleAll` 里那个新数组算 O(n)，但传进去的 `arr` 不算——它不是你的算法申请的。

# 三种情况：最好、最坏、平均

同一个算法，不同输入走的路可能差很多。三种情况都要会算：

```ts
// 在一个数组里找 target，返回第一个匹配的下标
function linearSearch(arr: number[], target: number): number {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i;
  }
  return -1;
}
```

- **最好情况 O(1)**：target 就在第一个位置，一次比较就返回。
- **最坏情况 O(n)**：target 在最后一个位置，或者根本不存在，要走完全程。
- **平均情况 O(n)**：假设 target 在每个位置等概率，期望比较次数约 n/2，去掉常数还是 O(n)。

**默认谈复杂度时，谈的是最坏情况。** 这是保守但安全的约定——你要对使用者承诺一个上界。一个「平均很快但偶尔爆炸」的算法，在实时系统里是不可接受的。

当然也有例外。快速排序就是典型：最坏 O(n²)，平均 O(n log n)，而实践中几乎总是跑在平均附近，所以它依然是排序的首选之一。但你在选它的时候，必须**知道**它有这个最坏情况，并且确认你的数据不会触发它。

# 均摊分析：单次很贵，长期很便宜

这是最容易被跳过、又极其重要的一个概念。

看动态数组（比如 JavaScript 的 `Array.push`）。单看某一次 `push`：如果刚好满了要扩容，它要把所有元素搬到新数组里，这一次是 **O(n)**。

那 `push` 到底是 O(1) 还是 O(n)？答案是 **均摊 O(1)**。

关键在于：**不要孤立地看单次操作，要看一序列操作的总代价。**

容量从 1 开始，每次翻倍：

```
第 1 次扩容：搬  1 个元素   （容量 1 → 2）
第 2 次扩容：搬  2 个元素   （容量 2 → 4）
第 3 次扩容：搬  4 个元素   （容量 4 → 8）
第 4 次扩容：搬  8 个元素   （容量 8 → 16）
...
第 k 次扩容：搬 2^(k-1) 个元素
```

n 次 `push` 触发的总搬运量是 1 + 2 + 4 + ... + 2^(k-1) ≈ 2n。所以**均摊到每次 push，是 O(1)**。

我用代码实测了这件事：

```ts
class DynamicArray {
  private buffer: (number | undefined)[];
  private length = 0;
  private copies = 0;

  constructor(initialCapacity = 1) {
    this.buffer = new Array<number | undefined>(initialCapacity);
  }

  get totalCopies(): number {
    return this.copies;
  }

  push(value: number): void {
    if (this.length === this.buffer.length) {
      const next = new Array<number | undefined>(this.buffer.length * 2);
      for (let i = 0; i < this.length; i++) {
        next[i] = this.buffer[i];
        this.copies++;
      }
      this.buffer = next;
    }
    this.buffer[this.length] = value;
    this.length++;
  }
}
```

实测输出：

```
push       1,000 次 → 搬运       1,023 次，平均每次 push 搬运 1.02 次
push      10,000 次 → 搬运      16,383 次，平均每次 push 搬运 1.64 次
push     100,000 次 → 搬运     131,071 次，平均每次 push 搬运 1.31 次
push   1,000,000 次 → 搬运   1,048,575 次，平均每次 push 搬运 1.05 次
```

搬运总量约等于 n，平均每次约 1 次出头。**单次最坏 O(n)，n 次均摊 O(1)。**

> 这里有个实现细节值得注意：必须用独立的 `length` 跟踪元素个数。如果图省事用 JS 数组的 `.length` 当容量，`new Array(cap * 2)` 一建出来 `.length` 就跳成了 `cap * 2`，容量跟踪会直接错掉——我第一版就栽在这，测出来「搬运 1 次」，完全不对。

# 实测：把纸上的结论跑出来

前面都是纸面推导。现在跑真的。

同一个问题「求 1 到 n 的和」，写六个版本，用「操作计数」精确度量：

```ts
class Counter {
  private count = 0;
  tick(n = 1): void { this.count += n; }
  get value(): number { return this.count; }
  reset(): void { this.count = 0; }
}
const ops = new Counter();

function sumFormula(n: number): number {          // O(1)
  ops.tick(3);
  return (n * (n + 1)) / 2;
}

function sumHalving(n: number): number {          // O(log n)
  let total = 0, remaining = n;
  while (remaining > 0) {
    ops.tick(2);
    total += remaining;
    remaining = Math.floor(remaining / 2);
  }
  return total;
}

function sumLoop(n: number): number {             // O(n)
  let total = 0;
  for (let i = 1; i <= n; i++) { ops.tick(2); total += i; }
  return total;
}

function sumQuadratic(n: number): number {        // O(n²)
  let total = 0;
  for (let i = 1; i <= n; i++)
    for (let j = 1; j <= n; j++) { ops.tick(1); if (i === j) total += i; }
  return total;
}
```

n = 1024 时的实测：

| 算法 | 大 O | ops(n) | ops(2n) | 倍数 |
| --- | --- | --- | --- | --- |
| 公式法 | O(1) | 3 | 3 | **1.00** |
| 折半累加 | O(log n) | 22 | 24 | **1.09** |
| 单层循环 | O(n) | 2,048 | 4,096 | **2.00** |
| 嵌套全遍历 | O(n²) | 1,048,576 | 4,194,304 | **4.00** |

**「n 翻倍，操作数变几倍」这个视角，比背任何定义都直观。** O(1) 不变，O(log n) 几乎不变，O(n) 翻倍，O(n²) 变四倍。

指数级单独看，因为 n 稍大就爆：

```
    n       ops(2^n)        相对上一行的倍数
   20      2,097,151                   —
   21      4,194,303                2.00
   22      8,388,607                2.00
   23     16,777,215                2.00
   24     33,554,431                2.00
```

n 每 +1，精确翻倍。n=30 就是 10 亿量级。

真实世界里最典型的指数级失误是**朴素递归斐波那契**：

```ts
function fibNaive(n: number): number {
  ops.tick(1);
  if (n <= 1) return n;
  return fibNaive(n - 1) + fibNaive(n - 2);
}
```

它的调用树不是满二叉树，增长率是黄金比例 φ ≈ 1.618 而不是 2，但依然是指数级：

```
    n           调用次数            相对上一行的倍数
   20         21,891                   —
   22         57,313                2.62
   24        150,049                2.62
   30      2,692,537                2.62
```

Δn = 2，所以倍数约 φ² ≈ 2.62。**n=40 就要算 3.3 亿次**，而用迭代写法是 O(n)。同一个结果，差了一个宇宙。

# 计时：比纸面推导更接近现实，但更容易骗你

操作计数是确定的，但它假设「每次操作一样贵」。现实里不是——缓存命中与否，能差出 10 倍以上。

所以也要看真实耗时：

```
n = 200,000，取 3 次最小值

算法            大 O                耗时(ms)
公式法           O(1)                0.000
折半累加          O(log n)            0.001
单层循环          O(n)                0.264
嵌套折半          O(n log n)          2.787
```

O(n) 和 O(n log n) 在 n=2e5 时只差约 10 倍。**但 n 再涨一个数量级，这个差距会按比例继续拉大。** 大 O 承诺的是趋势，不是这一个点上的表现。

O(n²) 的扩张更直观：

```
        n        耗时(ms)            相对上一次的倍数
    5,000         19.28                   —
   10,000        106.13               5.50x
   20,000        426.55               4.02x
```

n 翻倍，耗时趋向 4 倍。第一行 5.50x 偏高是 JIT 还没预热——**这正是计时最容易被骗的地方。**

所以我坚持三条：

1. **看趋势，不看点值。** n 翻倍时耗时变几倍，这个比值比绝对毫秒数有信息量得多。
2. **取多次最小值。** 单次计时会被 GC、其他进程、JIT 预热干扰，最小值最接近代码本身的成本。
3. **分清「实测」和「推断」。** 我实测的是这段代码在这台机器上的表现，不是「这个算法在任何机器上的表现」。

# 三个常见误区

**误区一：「O(n) 一定比 O(n²) 快」。**
错。前面那个 1000 倍常数的例子就是反例。正确表述：n 足够大时 O(n) 一定赢。而拐点在哪，取决于你扔掉的常数。

**误区二：「n 小就不用管复杂度」。**
半对，而且是最容易出事的那种半对。**代码会活下来，数据会长大。** 今天 n=100 的接口，明年可能就是 n=10 万。O(n²) 在 n=100 时跑 1 毫秒，在 n=10 万时要跑 10 万毫秒。先写对，但要留个心眼。

**误区三：「benchmark 快就是快」。**
错，而且是最隐蔽的错。上面的计时表第一行 5.50x 而不是 4x，就是 JIT 预热没做完。单次测量、单次对比、不同机器之间的数字，基本都不能直接比。要看趋势，要取最小值，要控制变量。

# 练习

按这个系列的规矩，不给标准答案，给验证方法。

**练习 1：两个看起来不一样的循环。**

下面两段代码，时间复杂度分别是多少？先自己数，再用操作计数验证。这两题凑成一对是有原因的——一个「看起来变了其实没变」，一个「看起来没变其实变了」。

```ts
// A：内层上限是 i，不是 n
function mysteryA(n: number): number {
  let count = 0;
  for (let i = 1; i <= n; i++) {
    for (let j = 1; j <= i; j++) {
      count++;
    }
  }
  return count;
}

// B：内层是 j += i，步长随外层变
function mysteryB(n: number): number {
  let count = 0;
  for (let i = 1; i <= n; i++) {
    for (let j = 1; j <= n; j += i) {
      count++;
    }
  }
  return count;
}
```

验证方法：用第一课的 `Counter` 数操作数，然后看 `ops/n` 随 n 怎么变。

- 如果 `ops/n` 是常数 → O(n)
- 如果 `ops/n` 对数级增长 → O(n log n)
- 如果 `ops/n` 线性增长 → O(n²)

我的实测结果（剧透，先自己数）：

```
A：ops/n = 500.5 → 1000.5 → 2000.5 → 4000.5   （线性增长）
B：ops/n =   8.05 →    8.75 →    9.45 →   10.14   （对数级增长）
```

**A 是 O(n²)。** 这一点最反直觉：内层上限从 `n` 变成 `i`，看着变了，其实只是把常数砍了一半——总次数是 1+2+...+n = n(n+1)/2，去掉 1/2 还是 Θ(n²)。

**B 是 O(n log n)。** 内层每次跑 ⌈n/i⌉ 次，总次数是 n/1 + n/2 + ... + n/n = n·H(n)，H(n) 是调和级数，等于 ln(n) + γ + o(1)，所以是 Θ(n log n)。

记住这个教训：**内层边界写成变量，不等于阶数会变。** 必须真的把总次数加起来看。

**练习 2：为什么第二个是 O(log n)。**
二分查找为什么是 O(log n)？用「每比较一次，候选区间减半」这句话，推导出最坏比较次数。

**练习 3：找出指数级。**
下面这个求第 n 个斐波那契的写法，为什么慢？改写成 O(n) 的。

```ts
function fib(n: number): number {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}
```

验证方法：用第一课的 `Counter` 数调用次数，对比 n=30 时两个版本的操作数差多少倍。

**练习 4：均摊的不是 O(1)。**
第一课的 `DynamicArray`，如果把扩容倍率从 2 改成 1.5，均摊复杂度会变成什么？改成 3 呢？想想「总搬运量」和「扩容频率」怎么互相牵制。
