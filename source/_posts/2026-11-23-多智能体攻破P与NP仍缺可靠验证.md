## 多智能体并行不等于问题已被解决

多智能体能并行探索更多方案，但复杂度难题要求每一步都能被可靠验证。我的判断很直接：没有验证器，增加智能体数量只是增加候选答案。

这条讨论来自 pequalnp.com，对应 Hacker News 条目编号为 50604314。页面获得 101 Points，相关评论有 93 条。热度说明不少人对“群体智能能否突破 P 与 NP”感兴趣，但讨论数量无法替代证明强度。

P 与 NP 的核心障碍并非算力不足。问题在于，NP 问题的解可以被多项式时间验证，是否也能被多项式时间找到，至今没有普遍答案。若多智能体通过分工、互评和反复尝试找到高效解，论文仍需回答：答案是否对所有实例成立？验证时间是否仍有界？失败来自搜索策略，还是问题本身没有高效解？

> 101 Points 和 93 条评论记录了关注度，却没有记录一个可复现的证明。

## 任务拆解解决的是搜索组织

把难题拆给多个智能体，确实可能改善搜索过程。一个智能体负责建模，一个负责构造解，一个寻找反例，另一个检查边界条件。每个角色都有明确输出，比让单个模型长时间自由探索更容易控制。

2026 年的 Agent 讨论也集中在执行能力。工具链已经能覆盖编程、办公和部分知识工作。这支持了“多智能体可以并行推进任务”的判断，却不能直接支持“并行推进可以解决 P 与 NP”。工作流变快，与数学证明变短，是两件事。

我也在做一人公司。AI 能搜集信息、拆解任务、写文档，还能同时推进几条工作线。但卡点始终具体：解决什么问题，谁付钱，怎么收钱。多个 Agent 可以并行产出候选方向，无法自动替代这三个判断。<span class="hl">我的 mem-md 召回命中率约 9%，也说明并行并不等于信息利用充分。</span>

> mem-md 的召回命中率约 9%。并行调用再多次，也可能反复漏掉关键约束。

真正困难的部分，是把候选解转成可检查的中间表示。SAT 求解器需要约束传播，回溯算法需要搜索树，线性规划需要可验证的最优性条件。多智能体若只交换自然语言结论，验证成本会随交流轮数上升。每个 Agent 都可能误读前提，也可能把另一个 Agent 的猜测当成事实。

因此，系统设计应先解决任务拆解后的状态表示、错误隔离和验证接口，再决定部署多少个 Agent。角色数量不是可靠性的来源。

## 可靠验证必须独立于生成过程

我最初会把多数票当作群体智能的保险。三个 Agent 同意，答案错误的可能性似乎更低。实际数学证明中，多数票没有证明力。三个模型可能共享同一套训练偏差，也会沿着相同的错误路径继续搜索。

可靠的验证器需要满足几个条件。它不能依赖生成答案的同一个 Agent；失败必须能定位到某条约束或某个推理步骤；反例输入应被保留；所有提交都可以重复运行。<span class="hl">生成与验证分离，比单纯扩到 10 个或 100 个 Agent 更重要。</span>

这里可以借鉴工程测试的思路。单元测试无法证明程序绝对正确，却能排除一批具体错误。形式化验证也不能覆盖所有系统，但能对给定模型提供严格保证。P 与 NP 研究需要的正是这种方向的验证基础：每个关键声明都能由较小的检查器确认，或者由明确的反例推翻。

> 一个可复现的反例，比 100 份措辞一致的 Agent 草稿更有价值。

多智能体系统还应保存失败轨迹。一次搜索失败，说明某个候选解不成立，不必连带否定整个任务。问题描述含糊、约束遗漏和证明失效，需要分别记录。否则系统只会累积越来越长的讨论，却不知道下一次该改哪里。

## 把群体智能看成实验系统

群体智能适合扩大探索范围，也适合并行检查弱化后的候选答案。它不能绕过复杂度下界，也不能替代完整证明。把它直接称作“攻克 P 与 NP”，会把工程进展和数学结论混在一起。

更准确的定位，是把多智能体组织成实验系统。任务拆解必须留下可检查的约束，Agent 交换结构化状态，验证器独立运行，失败结果进入下一轮搜索。系统报告探索范围、失败类型和验证结果，不输出无法复核的“已经解决”。

这套结构对创业和日常工作同样有用。多个 Agent 可以压缩准备时间，但最终交付仍需要验收标准。代码要测试，数据要核对，费用要确认。缺少验收环节时，产出越多，错误只会藏得更深。

到 2026 年 11 月 23 日，我仍然无法判断群体智能会不会找到新的通用算法。多智能体缺少可靠验证时，它更适合提出更多假设。

真正值得追踪的指标或许包括：多少候选解通过了独立检查，失败能否快速定位到具体约束，以及整套流程能否重复运行。多智能体能否突破复杂度难题，最终取决于这些数字，而不是参与协作的 Agent 数量。
