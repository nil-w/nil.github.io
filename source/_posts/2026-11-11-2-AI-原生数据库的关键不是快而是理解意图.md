## 上下文决定数据库能不能接住意图

AI 原生数据库的核心能力，在于把用户意图落实到正确的数据操作上。

我在《从零构建 Hermes Agent 记忆系统——memory-filtration-layer 迭代手记》（2026-05-22）里处理过一类具体故障。系统记得很多内容，却经常检索不到真正需要的信息。用户换了表达，记忆就像断开了。

这件事让我意识到，Agent 的执行质量取决于系统能否维持稳定的语义关联。数据库如果只能按字段匹配，就很难独立支撑 Agent。

> 旧问题不是存储量不足，而是“截图工具”和“微信截图”没有落进同一个可检索语义单元。

上下文工程也不只是 Prompt 技巧。《大模型入门 04｜上下文工程与 Agent 可靠性》（2026-11-10）已经讨论过模型如何获得完成任务所需的信息。

数据库承担的角色很具体。它需要把当前请求、历史对话、业务规则和可用数据组织起来，再交给 Agent 决定调用。

<span class="hl">数据库要理解的是一次操作中的上下文关系。</span>

传统查询要求调用方先知道表名、字段名和关联方式。Agent 面对自然语言请求时，这些信息通常散落在用户表达、历史记录和业务规则里。

例如，用户说“找出上个月仍未处理的有效订单”。系统至少要识别时间范围、订单状态、业务有效性，以及“未处理”的具体含义。

每个条件都要映射到可执行的数据动作。任一映射含糊，结果就会偏离原意。

> 一个自然语言要求，至少会落到时间、状态、规则和数据范围四类约束上。

## 语义层承担从表达到操作的转换

数据库需要提供一层稳定的语义接口，让 Agent 不必猜测物理结构。

这层接口至少应表达实体、关系、动作与约束。用户提到“客户”时，系统需要知道它对应什么对象。用户要求“冻结账户”时，系统需要知道影响哪些记录、允许哪些状态变化。

权限边界也必须进入上下文。Agent 能否查看完整信息，能否执行写操作，能否使用敏感字段，都应该在调用前明确。

<span class="hl">理解意图必须包含理解操作权限。</span>

我在《改造 Hermes Agent 记忆系统：基于 MemPalace 的实践》（2026-05-01）里改过 key-value 存储。固定 key 适合简单读取，却难以处理同义表达、实体关联和上下文变化。

记忆系统已经暴露出语义层缺失的问题。业务数据库若只提供表和字段，这个问题会继续留在 Agent 侧。

Agent 每次临时生成 SQL，会带来更多不稳定因素。同一句请求可能得到不同查询逻辑，复杂约束也容易被遗漏。数据库需要把常用语义和关键约束沉淀下来。

这一步无法完全替代模型判断，却能减少模型反复解释业务结构的负担。

> 可靠执行的标志，是同类请求能落到一致的查询范围和操作边界。

## Agent 可靠性依赖可验证的执行过程

我的初步判断是，AI 原生数据库会先在语义层成熟，再逐步进入执行闭环。现在我还不能确定最终产品形态。

但 Agent 的执行过程必须留下可检查的记录。数据库不能只返回答案，还要保留这次调用依据了哪些上下文，采用了什么数据范围，以及触发了哪些业务规则。

这会直接影响错误处理。查询无结果、语义冲突和权限不足，需要分别反馈。Agent 才能修正请求，而不是反复提交相似操作。

写入操作更需要验证。Agent 从意图中识别出“更新”，不代表可以直接覆盖原数据。系统需要检查对象是否存在、当前状态是否允许修改，以及操作是否超出授权范围。

<span class="hl">Agent 的可靠性来自意图、执行和反馈能够对齐。</span>

《Hello Hermes Agent》（2026-04-27）记录了我对 Agent 系统的早期兴趣。那时我更关注工具能否调用起来。现在我会先追问：工具调用是否建立在准确的数据语义上。

这改变了我的评估顺序。响应速度依然重要。意图识别错了，查询完成得再快，也只是更快地交付错误结果。

我到现在也没想清楚，语义理解应主要放在数据库、Agent，还是两者之间。实践已经给出一个方向：数据库必须拥有足够稳定的语义描述，让 Agent 的每次执行都能被约束和验证。

下一次评估 AI 原生数据库，我会先看它能否接住请求中的关系、规则与权限，再看查询性能。
