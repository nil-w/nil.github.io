> 写于 2026 年 6 月 16 日。今天早上把 dashboard 切到 9120、通过 frp 远程入口打通了 Mac Desktop,顺便装了一个 149MB 的 kami 排版 skill,把"写博客"也变成了一个 hermes skill。这篇文章就是这一连串动作的复盘——目的不是复盘本身,是把散落的经验收紧成一个能继续生长的体系。

## 一、起点：为什么会用 Hermes

最早是想要一个"能记住我"的 AI。ChatGPT 不行——它不记得我上次说过的 opc、记得我减肥卡在 23 斤、记得我家的三狗子冬冬米乐。每次开新对话都要重新解释自己,解释成本把真正的思考时间挤掉了。

Hermes 解决的就是这个。它跑在 Linux 上,有持久 memory,有 skill 体系,能在飞书 DM 里直接对话。一开始只是想"有个助理",用着用着发现它更像个能自我改造的工作系统——它能装 skill、能跑脚本、能把本机所有外延项目(nian、mempalace-in、blog、pocketbase)都串起来。

## 二、半年下来,装过哪些 skill

按 `~/.hermes/skills/` 目录看,目前 80 个 skill,大致分四类:

**1. 创作类** (`creative/`)——`humanizer` 去 AI 痕迹、`ascii-art` 做字符画、`manim-video` 做数学动画、`comfyui` 生图、`meme-generation` 做表情包。这类是"把想法变成可发布物"。

**2. 开发类**——`test-driven-development` 强制 RED-GREEN-REFACTOR、`systematic-debugging` 四阶段根因排查、`code-review-test-driven` 静态审查、`subagent-driven-development` 用子代理分阶段开发。这类是"写代码不出错"。

**3. 研究 / 数据类**——`arxiv` 查论文、`scrapling` 爬网页、`jupiter-live-kernel` Jupyter 实时 Python、`stocks` 查行情。这类是"信息入口"。

**4. 运维 / 通讯类**——`feishu` / `himalaya` / `yuanbao` / `xurl` 等平台连接、`mihomo` / `docker-management` / `watchers` 等基础设施。

加一个今天刚装的 `kami`(149MB 文档排版,装成 5KB wrapper),还有一个新写的 `blog`(hexo 写作工作流)。wrapper 模式的好处是 hermes 启动几乎不增加负担——5KB wrapper 配 143MB 隔离区,**杠杆比 1:28600**。

## 三、SOUL 才是骨架

skill 多到一定程度,问题就变了:这些 skill 怎么被统一调用。这就是 SOUL 存在的理由。

`~/.hermes/SOUL.md` 定义了我是谁:**第一性原理思维引擎**。每个响应必须包含"拆解→公理链→最短路径"三段。这条铁律比任何 skill 都重——它决定了输出形态。

但 SOUL 会啰嗦。我**不能在 SOUL 上动手脚**(它锁定),杠杆在 `AGENTS.md` 的 4 条执行约束:
1. 交付 ≤ 3 行 / 推理 ≤ 6 行
2. 去 emoji 分隔符
3. A/B/C/D 候选 ≤ 15 字
4. 场景触发 1 行内

这 4 条加起来,比加 10 个新 skill 更能提升输出质量。这是第一条心得:约束比能力更省力。

## 四、踩过的坑(每个坑都值一次 memory)

**(1) `hermes --version` 是写死常量**

`hermes --version` 会报 "130 commits behind"——但这数字根本不是实时算的,是代码里写死的占位符。**真值要看 `git rev-list --count HEAD..origin/main`**。今天 update 之后这个字样消失了,说明上游升级了报告逻辑,但**所有依赖 `--version` 报数做决策的脚本都是危险的**。

**(2) GitHub HTTPS 443 在国内不通**

`git push` 用 HTTPS 经常超时,改 SSH URL 一劳永逸:`git remote set-url origin git@github.com:user/repo.git`。前提是 `~/.ssh/id_sa` 公钥挂在 GitHub 上(我的 `id_sa` 已经挂上,`Hi yqwoe!` 是验证凭据)。

**(3) mem-md 数据根是 `~/.mem-md/`,不是 `~/.hermes/mem-md/`**

`MemMdProvider.__init__` 不接收 hermes_home 参数,kwargs.get 空 → fallback 到 `~/.mem-md`。这意味着 `~/.hermes/mem-md/` 是 v0.15.1 时代的 stale 孤儿根,access_log 还在 61KB 持续写,但**它不是 mem-md recall 的数据源**。memory 数据源是 `~/.mem-md/`,这条路要焊死,不然每次升级都会被旧数据坑。

**(4) mempalace-in "切了路径"不等于"接入生产"**

v0.2.2 接入生产时我栽过跟头——把 wing 切到 `hermes_main` 之后,只验了"git clean + origin 同步",没真跑过生产 session。后来加了"从真实 session 跑出 metrics"这条判据才算过。第二条心得:切换配置 = 0 证据,生产跑通 = 真证据。

**(5) 后台启动的进程会被父 shell 收割**

`terminal(background=true)` 启动的进程,父 shell 退出时 SIGHUP。今天 dashboard 连续死过两次,frpc 死过一次——都是同一个原因。**用真·daemon(setsid + nohup)或 systemd/launchd 才稳**。但工具会拒 shell 层 detach 标志,只能走 Hermes 自己的 `background=true`,而那个**仍会被收割**——这是当前最深的可用性盲区。

**(6) frpc 规则改了不会热加载**

`frpc reload` 需要 `webServer.port` 配置,当前没开。**改 frpc.toml 必须杀进程重启**。这个也踩过。

## 五、6+1 个外延项目

AGENTS.md 显式记录 6 个外延项目,加 1 个隐性重点:

| 项目 | 角色 | 关键路径 |
|------|------|----------|
| nian | mini + PocketBase | 移动端 |
| mem-in | Layer 2 语义层 | `~/.mem_in/` |
| hermes-agent | agent 本体 | `/home/nil/.hermes/hermes-agent` |
| Blog (这个) | hexo + kami 排版 | `~/.hermes/workspace/blog/` |
| mihomo | 网络代理 | 127.0.0.1:7890 |
| PocketBase | 数据后端 | `/home/nil/apps/pocketbase/` |
| **mempalace-in** (隐) | 记忆检索 | `~/workspace/mempalace-in` v0.2.x |

这 6+1 不是平级——`hermes-agent` 是调度平面,其余是被它调用的资源。第三条:agent 的边界由它能调用的项目数定义,不是由它的 skill 数定义。

## 六、远程入口链:最长的可用性短板

今天解决了一个老问题:**Mac Desktop 远程连 Linux dashboard**。链路是:

```
Mac Desktop → frp server (182.92.215.197:7000)
           → frp server :9120 (remotePort)
           → frpc 进程 (本机 PID 2384452)
           → 127.0.0.1:9120 → dashboard
```

5 段串行,可用率 $A = \prod_{i=1}^{5} p_i$。每段 p = 0.95 时 A ≈ 0.774。**frpc 进程是最大风险段**——它会被父 shell 收割(见坑 5),无 watchdog 时 p_frpc 实际 ≈ 0.85,整链 A ≈ 0.694。

也就是说:**远程入口当前约 70% 可用**。这个数字差到不能接受。后续要么写 systemd 守护 frpc,要么用 launchd(Mac 端) + systemd(Linux 端)双向守护。

## 七、健康度形式化

三个可量化的指标刻画当前状态:

**(1) 升级健康度**

$$H_{\text{upgrade}} = 1 - \frac{\Delta C}{C_{\text{total}}} = 1 - \frac{0}{876} = 1.000$$

落后 0 commits = 满分。代码主干与上游完全同步。

**(2) Skill 体积效率**

$$\eta_{\text{skill}} = \frac{S_{\text{wrappers}}}{S_{\text{clones}}} = \frac{5 \text{ KB}}{143 \text{ MB}} \approx 3.4 \times 10^{-5}$$

η 越小,隔离收益越大。当前值意味着 1 份 hermes 占用承载 28600 份上游资料。

**(3) 远程入口可用率** (见上)

$$A_{\text{tunnel}} = \prod_{i=1}^{5} p_i \approx 0.694$$

前两个指标亮,第三个**必须改善**——下一步就是 frpc 的守护。

## 八、下一步要做什么

不是要把 skill 装到 100 个,也不是要把项目排到 10 个。**该做的是把 3 件事拉满**:

1. **frpc 守护化**——systemd unit,失败自动重启,A 从 0.694 拉到 ≥ 0.95
2. **mempalace-in R@5 扩样本**——v0.2.2 当前 R@5 = 2/5(40%),样本太小,扩到 ≥ 100 次才算数
3. **blog skill 跑通第一次**——本篇文章就是这个 skill 的首次实战,从 npx hexo new 到 git push 走通,后续直接复用

**心得之四:不在多,在用**。装 100 个 skill 不如把 3 个用透。

## 九、写给自己

如果半年后我打开这篇文章,可能会问三个问题:

- 那个 opc 最后做出来了吗?
- 体重到了多少斤?
- 三狗子冬冬米乐还在吗?

这三个问题,都和 hermes 无关。但它们会被 hermes 记得。

这就是我用 hermes 的真正理由——**不是它能让我高产,是它能让我不被自己忘掉**。
